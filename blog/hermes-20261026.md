# Recap de Hermes — semana del 26 de octubre al 1 de noviembre de 2026

Esta fue una semana centrada casi por completo en convertir Skynet de una plataforma capaz de ejecutar agentes en una fábrica de software conectada de verdad con GitHub. El avance no fue una única función: se cerró el circuito completo entre repositorios, workflows, agentes reales, pull requests, CI, gates, merge y notificaciones operativas.

## La semana en cifras

La minería de actividad de Hermes, acotada por timestamps al periodo del lunes 26 de octubre al domingo 1 de noviembre, encontró:

- 73 prompts humanos.
- 18 sesiones.
- 855 llamadas a herramientas.
- 749 llamadas API.
- 14 pull requests fusionadas en `guilu/skynet`.
- 5 pull requests fusionadas en `guilu/skynet-commands`.

Los prompts son un índice de actividad, no evidencia de entrega. Las cifras de pull requests se contrastaron con GitHub y las entregas principales con el historial Git, los informes de aceptación y el estado desplegado.

## Skynet completó su capa visual y de identidad

El lunes se fusionaron las dos piezas restantes de la galería visual de Skynet:

- VS-B añadió un mapa visual de navegación.
- VS-C añadió composiciones preparadas para compartir en redes sociales.

Con ello, el generador de capturas dejó de ser solo una herramienta de prueba. Pasó a servir también para documentar el producto, revisar el diseño de sus distintas secciones y producir material reutilizable sin capturar datos privados de una instalación real.

La mascota también dio un salto importante mediante tres entregas consecutivas:

- SY-A incorporó Skyny v3, con dibujo, colores, animaciones y accesorios.
- SY-B convirtió a Skyny en el icono de la aplicación.
- SY-C añadió nuevas interacciones.

La aceptación de SY-C terminó con los 12 checks de CI en verde. Después del merge se reconstruyeron y desplegaron API y web, se validaron las migraciones y se restauró el runner real.

La pantalla de Uso recibió además los logotipos de Claude Code, Codex y Antigravity mediante LG-A. La aceptación comprobó los SVG, sus colores, el centrado de las baldosas de 48×48 píxeles y la vista móvil oscura sin desbordamiento. Vitest ejecutó 10 pruebas específicas con éxito.

## La documentación generada por agentes pasó a ser memoria de proyecto

MP-A añadió un mapa del repositorio por proyecto. El objetivo era resolver un problema práctico: los workflows podían generar documentación —por ejemplo, `docs/skynet/mapa-sky.md`— pero el usuario necesitaba que ese conocimiento permaneciera accesible dentro de Skynet y no solo como un archivo descargable o efímero dentro de un workspace.

La entrega estableció la base para asociar el mapa del repositorio al proyecto y reutilizarlo como contexto. Su CI completa quedó en verde y la aceptación se ejecutó sobre el SHA exacto de la PR, con PostgreSQL, API y web saludables y el runner real restaurado al terminar.

## El runner real se convirtió en una condición operativa, no en una esperanza

Al principio de la semana apareció un riesgo recurrente: las pruebas de aceptación podían levantar runners simulados y dejar la instalación en un estado que parecía saludable, pero no estaba preparada para ejecutar Claude Code, Codex o Antigravity reales.

Se creó un helper idempotente de restauración y verificación del runner real y se integró como paso obligatorio en el flujo del webhook. A partir de ahí, cada aceptación debía terminar comprobando:

- un único runner `omarchy` online;
- Claude Code real;
- Codex CLI real;
- Antigravity real;
- `simulated=false` para todos;
- ausencia de procesos fake residuales.

Los informes posteriores verificaron repetidamente ese contrato. En el cierre de EN-C estaban activos Claude Code 2.1.310, Codex CLI 0.164.0 y Antigravity 1.4.12.

También se discutió el control de cuota. La conclusión importante fue que restaurar agentes reales no debía equivaler a permitir ejecuciones ilimitadas: los límites tienen que vivir en el orquestador, con presupuestos, gates y estados persistentes, y no depender de una instrucción informal dentro del prompt.

## Reset limpio sin confundir datos operativos con memoria

Se realizó un reset de Skynet para dejar la instalación limpia y conservar únicamente los workflows iniciales. La operación obligó a distinguir varias clases de estado:

- datos transaccionales y ejecuciones que sí deben poder limpiarse;
- definiciones iniciales que deben reconstruirse de forma determinista;
- memoria y documentación útil del proyecto, que no deben desaparecer accidentalmente;
- configuración y secretos, que nunca deben formar parte de un reset de datos.

Esta separación se volvió especialmente relevante al mismo tiempo que MP-A convertía documentación generada en memoria reutilizable.

## GitHub App: autenticación real para repositorios y workflows

Skynet incorporó su integración nativa con GitHub en tres entregas.

### GH-A — App y tokens de instalación

Se añadió el modelo de GitHub App y la obtención de tokens de instalación. La aplicación real se creó manualmente en GitHub, se configuraron sus permisos y se instaló en el repositorio de Skynet. La clave privada se mantuvo fuera del repositorio y de los logs, con una copia local de respaldo bajo permisos restringidos.

La integración permite que los proyectos de Skynet referencien repositorios GitHub sin reutilizar un token personal de larga duración. Los tokens de instalación son temporales y limitados a los repositorios y permisos concedidos a la App.

### GH-B — Webhooks firmados

La segunda entrega añadió recepción de eventos firmados. La aceptación comprobó, entre otros casos:

- rechazo de firma inválida con HTTP 401;
- aceptación asíncrona de un ping firmado;
- idempotencia por identificador de entrega;
- ignorado seguro de repositorios desconocidos;
- endpoint privado, ligado solo a loopback;
- comportamiento 503 cuando la App no está configurada.

Tras el merge se validaron 31 migraciones y se mantuvo la topología privada: PostgreSQL sin puerto publicado, API limitada a loopback y web disponible solo por loopback/LAN autorizada y Tailscale.

### GH-C — Ajustes de GitHub, web y E2E

La tercera entrega completó la experiencia web y los E2E. La aceptación pasó 436 pruebas Vitest y un E2E de GitHub en Chromium, además de toda la matriz de CI. El origen GitHub quedó visible en la actividad y las pruebas aprendieron a filtrar correctamente esos eventos.

Durante este trabajo también se actualizó la CI para ejecutar E2E y capturas sobre Ubuntu 24.04.

## Skynet aprendió a entregar cambios mediante pull requests

Las tres entregas EN-A, EN-B y EN-C completaron el ciclo de entrega de software.

### EN-A — Subir una rama y abrir la PR

Skynet pasó a poder publicar la rama generada por un workflow y abrir una pull request. La aceptación inicial falló porque el runbook buscaba literalmente `a + b` en `calc.py`, aunque el workspace heredado no contenía el cambio esperado. El fallo fue útil: reveló que una aceptación de integración no puede asumir datos residuales de una ejecución previa.

Se decidió que el escenario debía preparar y limpiar su propio repositorio de demostración. Una prueba reproducible puede crear un repo temporal, usarlo durante el flujo y eliminarlo al final; depender de un `demo-repo` mutable convierte el test en una lotería.

### EN-B — Esperar la CI y corregirla

La siguiente fase añadió la espera de checks y el bucle de corrección. El agente ya no da por terminada su tarea al subir código: debe observar el gate, interpretar fallos y volver a trabajar cuando corresponda.

### EN-C — Fusionar después del gate

La última fase añadió el merge condicionado al resultado del gate, junto con web y E2E. La aceptación final ejecutó las pruebas Java contractuales, 16 pruebas Vitest y el E2E de entrega. También verificó que el flujo local sin GitHub siguiera funcionando: la ejecución terminó correctamente, omitió las fases GitHub y no mostró una tarjeta de PR inexistente.

La PR #205 se fusionó con toda la CI en verde. `main` quedó desplegada en el commit `280ca12`, los tres contenedores quedaron saludables y el runner real volvió a quedar online.

## Un puente seguro desde GitHub Issues hasta Skynet

En paralelo se creó el repositorio privado `skynet-commands`. Su primera capacidad convierte una GitHub Issue autorizada en una solicitud compatible con Skynet.

El puente se diseñó deshabilitado por defecto y con una máquina de estados duradera. No basta con recibir un webhook y llamar a una API: el sistema debe sobrevivir a reinicios, reintentos, respuestas ambiguas y fallos parciales sin crear dos work items ni lanzar dos veces el mismo workflow.

La primera entrega pasó por varias rondas de TDD y revisión adversarial. Entre los aspectos endurecidos estuvieron:

- firma y autorización de webhooks;
- validación de política y esquema;
- idempotencia y reconciliación después de respuestas ambiguas;
- leases y claims atómicos;
- límites finitos para polling y reintentos;
- separación entre creación del work item, lanzamiento, seguimiento y notificación;
- pausa segura de todos los efectos cuando la configuración está deshabilitada;
- mensajes de fallo sanitizados;
- ausencia de secretos en logs y respuestas.

Cuatro PR pequeñas corrigieron después el puerto configurable, el bind privado y el tipo de work item usado por la API real. El resultado desplegado escucha únicamente en la interfaz privada de Tailscale y mantiene el lanzamiento controlado por un interruptor explícito.

## Telegram se convirtió en parte del circuito, pero no de la transacción principal

El siguiente requisito fue recibir en Telegram tanto la llegada del webhook como el resultado final. La implementación inicial reveló un problema clásico: enviar a Telegram durante la petición HTTP puede aumentar la latencia y acoplar la disponibilidad del puente a un servicio externo.

La solución fue una outbox SQLite duradera. La recepción del webhook valida, persiste su decisión y encola la notificación; un worker separado reclama y entrega los mensajes. Los estados terminales y su notificación final se guardan atómicamente para evitar perder el mensaje en la frontera de un crash.

La revisión adversarial cubrió:

- recuperación de leases;
- compare-and-swap mediante token de claim;
- migraciones compatibles con la base existente;
- reintentos sin relanzar el workflow;
- notificaciones de duplicado, deshabilitado y encolado;
- inclusión segura del resultado real de Skynet;
- escape HTML y límite verificable de 4096 caracteres;
- ausencia de tokens en logs;
- prevención de bucles ocupados y procesos zombi en el healthcheck.

La PR #11 fusionó esta capacidad. Los mensajes de Telegram informan de recepción y resultado, mientras que un fallo de notificación queda aislado y nunca provoca una segunda ejecución en Skynet.

## Operación doméstica: Black, Tailscale y una pantalla física compartida

La Raspberry Pi `black` se quedó colgada y tuvo que reiniciarse físicamente. Después se revisó el resto de equipos de red y se renovó Tailscale en las tres Raspberry Pi.

El acceso SSH desde el Mac mostraba primero un aviso por no negociar un intercambio de claves poscuántico y después parecía quedarse bloqueado. El problema real estaba en la interacción entre el login y tmux. Se terminó configurando `black` para que el acceso SSH y la consola física `tty1` compartan la sesión `main`.

La validación final dejó:

- la pantalla física conectada a tmux `main`;
- `btop` visible en esa sesión;
- SSH entrando en la misma sesión, de modo que los comandos se ven en ambos terminales;
- Tailscale renovado en las Raspberry afectadas.

La lección fue distinguir una sesión SSH realmente bloqueada de una sesión que se ha adjuntado a tmux sin presentar el prompt esperado.

## Omarchy: actualización lista, reinicio con una dependencia humana incómoda

Se ejecutó una actualización de Omarchy y se comprobó si el sistema requería reinicio. Apareció un riesgo operativo más importante que la actualización: tras reiniciar, el equipo se detiene en el login gráfico y ni la sesión de usuario, ni Hermes ni los servicios asociados arrancan hasta introducir físicamente la contraseña.

Como el ordenador está dentro de un armario de acceso incómodo, el reinicio se pospuso. Quedó pendiente diseñar una solución segura que no convierta el autologin en una degradación silenciosa de la seguridad y que permita recuperar Hermes y los servicios después de un reboot sin intervención presencial.

## Alexa y Home Assistant: reducir exposición en vez de compartirlo todo

Tras recuperar la integración privada de Home Assistant con Alexa, aparecieron dispositivos duplicados y una exposición excesiva de entidades. Se cambió el enfoque para filtrar la skill y compartir inicialmente solo los aires acondicionados.

Alexa no ofrecía una eliminación masiva cómoda de los dispositivos antiguos, por lo que parte de la limpieza siguió siendo manual. La decisión arquitectónica útil fue no exponer todo Home Assistant por defecto: la lista publicada debe ser explícita y mínima.

## Lowlights y fallos que aportaron información

- La aceptación de EN-A dependía de contenido heredado y falló al no encontrar `a + b`. Se convirtió en un escenario aislado y reproducible.
- Las pruebas con repositorios reales demostraron que crear y borrar fixtures es preferible a mantener un repo demo mutable compartido.
- Las primeras notificaciones de Telegram estaban demasiado acopladas a la petición del webhook. La outbox duradera corrigió latencia, recuperación y duplicados.
- Los runners simulados podían sobrevivir a una aceptación. La restauración del runner real pasó a ser un invariante obligatorio antes de avanzar la cola.
- El reset de Skynet volvió visible la necesidad de separar ejecuciones, memoria, configuración y secretos.
- Black no estaba simplemente “sin SSH”: tmux y `tty1` hacían que el estado interactivo fuera ambiguo.
- El reinicio de Omarchy sigue teniendo un punto único de intervención humana en el login gráfico.

## Aprendizajes

1. Un workflow de entrega no termina al generar código. Termina cuando el cambio está publicado, la CI ha pasado, el gate se ha respetado y el estado final es observable.
2. Las pruebas de aceptación necesitan fixtures autocontenidos y limpieza explícita. Reutilizar un repositorio mutable oculta dependencias y produce falsos fallos.
3. La integración con GitHub debe usar identidad de aplicación, permisos mínimos, tokens temporales y webhooks firmados; no un token personal omnipotente.
4. Los efectos externos necesitan máquinas de estado duraderas. Idempotencia, reconciliación y outbox son requisitos funcionales, no optimizaciones posteriores.
5. Una notificación no debe gobernar la ejecución. Telegram puede fallar y reintentarse sin repetir trabajo ni alterar el resultado de Skynet.
6. Los tests que cambian el entorno deben restaurar al final el runner real y demostrarlo con datos de la API.
7. La memoria de proyecto debe sobrevivir a resets operativos, pero seguir separada de credenciales y estado transaccional.
8. La recuperación remota de una máquina importa tanto como la actualización. Un reboot no está realmente automatizado si el sistema queda esperando una contraseña física.
