La semana del 19 al 25 de octubre fue la semana en la que Skynet dejó de limitarse a ejecutar workflows y empezó a conservar el contexto, los resultados y hasta una presencia visible de lo que hacen sus agentes. La Fase 2 se cerró con un editor visual completo; después llegaron la revisión de código con proveedores reales, los artefactos descargables, la memoria persistente, una mascota que convierte el estado de las ejecuciones en señales comprensibles y una nueva capa de identidad visual. Fuera del producto, se recuperó la integración privada entre Home Assistant y Alexa y un incidente de memoria en Omarchy produjo varias lecciones de operación que ya se tradujeron en mejoras concretas.

El índice semanal de Hermes contabiliza 88 prompts humanos en ocho sesiones principales, 524 llamadas a herramientas y 706 llamadas de API. Son métricas de actividad, no de entrega. Para esta nota se contrastaron los resultados con GitHub, Git, los runbooks de aceptación, los servicios desplegados y las sesiones del webhook. GitHub registra 23 PR de Skynet fusionadas durante el periodo. Los comandos periódicos y las operaciones repetitivas sin contenido editorial se han dejado fuera.

## La Fase 2 terminó con un editor visual completo

La semana comenzó terminando la integración de los tres proveedores reales. Antigravity sustituyó a Gemini CLI y la aceptación AR-C comprobó de extremo a extremo que Claude Code, Codex y Antigravity podían ser ejecutados por el runner, con sesiones, resultados estructurados, costes y evidencias verificables. Las pruebas no se conformaron con que un proceso terminase con código cero: comprobaron qué proveedor se había utilizado, qué modelo aparecía registrado y qué artefactos quedaban asociados a la ejecución.

Después se completó W8, la última pieza del editor visual de workflows. W8-A añadió el motor de edición y la representación de problemas en el grafo; W8-B permitió editar visualmente las fases; W8-C completó agentes, entradas y creación de workflows desde cero. La aceptación creó versiones sucesivas de un workflow, publicó y ejecutó ambas y verificó que las ejecuciones antiguas seguían vinculadas a su versión original. Con ello la Fase 2 quedó cerrada: Skynet ya no solo interpreta definiciones, sino que permite construirlas, validarlas, versionarlas y ejecutarlas desde la interfaz.

La aceptación de W8 produjo también un fallo operativo útil. Había dos runners nativos activos al mismo tiempo y podían competir por los comandos. El worker autónomo se detuvo cuando una inspección pidió aprobación interactiva. La recuperación eliminó las unidades antiguas y dejó un único runner supervisado. La regla quedó clara: una revisión desplegada, una versión del runner y un único consumidor activo.

## Un reset real para empezar limpio

Tras semanas de pruebas, la aplicación conservaba proyectos, repositorios, ramas, worktrees, ejecuciones y workflows históricos. AL-A añadió un arranque limpio que elimina el estado temporal y vuelve a publicar los workflows iniciales. Antes de ejecutar el reset real se utilizó un dry-run para enumerar exactamente qué iba a desaparecer.

La primera prueba descubrió rutas históricas que ya no eran repositorios Git válidos. En vez de intentar podarlas o ejecutar comandos Git a ciegas, el script aprendió a comprobar que la ruta existe, es un directorio accesible y pertenece a un repositorio válido. Las rutas obsoletas se omiten con una advertencia y no bloquean el resto de la limpieza.

El reset también expuso un riesgo de infraestructura: sin contexto, Compose podía recrear PostgreSQL usando el archivo base y publicar el puerto estándar en el host. Se corrigió en una PR específica para que el script detecte en los contenedores existentes los archivos Compose y el archivo de entorno utilizados por el despliegue privado. De este modo conserva el override que mantiene PostgreSQL sin puertos publicados, la API en loopback y la web únicamente en loopback y la interfaz LAN autorizada.

## La revisión real pasó de demo a frontera de seguridad

El siguiente bloque de trabajo nació de una ejecución real de revisión de código. La primera implementación no se limitó a producir observaciones: también reveló qué ocurre cuando un agente revisor dispone de herramientas, rutas y salida estructurada en un entorno que no debe modificar.

La incidencia se convirtió en una serie de cuatro entregas, RV-A a RV-D. Se endurecieron permisos, validación de rutas y repositorios, operaciones Git, parsing de salida estructurada, tratamiento de secretos, entradas del workflow, aislamiento del runner y despliegue. El principio fue que un revisor debe poder inspeccionar y explicar, pero no adquirir permisos de escritura por accidente ni convertir una cadena de entrada en autorización para operar fuera de su ámbito.

Las aceptaciones verificaron los arreglos con agentes reales y no solo con dobles deterministas. También distinguieron los defectos de una PR de lo que pertenecía a entregas posteriores, evitando bloquear una fase por requisitos que estaban explícitamente planificados en otra. Esta separación convirtió un fallo difuso en una secuencia revisable y comprobable.

## Un repositorio mínimo para probar agentes sin quemar tiempo

Las primeras aceptaciones reales utilizaban el propio repositorio de Skynet. Era una prueba cara: mucho código, contexto amplio y ejecuciones lentas para comprobar comportamientos relativamente pequeños. Se creó `demo-repo`, un proyecto Python deliberadamente pequeño con un analizador de texto y pruebas sencillas.

El repositorio se registró como un proyecto de demostración dentro de Skynet y pasó a ser el objetivo de las pruebas de agentes reales. Esto permitió verificar lectura, análisis, salida estructurada, memoria y artefactos con un coste y una duración mucho menores, sin permitir que un runbook autónomo modificase el repositorio principal. En una ejecución posterior, Claude Code analizó el proyecto, devolvió mejoras estructuradas y dejó el HEAD y el worktree exactamente como estaban.

La lección es generalizable: las pruebas de infraestructura de agentes necesitan fixtures a escala de repositorio, no solo fixtures de texto. Un repositorio pequeño y determinista permite observar herramientas, permisos, commits, artefactos y consumo sin convertir cada aceptación en una sesión de desarrollo completa.

## Los artefactos dejaron de ser rutas invisibles

Una ejecución generó un documento Markdown dentro de su workspace, pero la interfaz solo mostraba la ruta. No había forma de abrirlo ni descargarlo. La discusión de producto evitó la solución fácil de tratar cualquier fichero modificado como artefacto: solo deben capturarse los archivos que una fase declara explícitamente como resultado.

AG-A implementó la captura y descarga segura de esos archivos declarados. AG-B llevó los resultados a la web. La aceptación comprobó Markdown, imágenes y otros tipos previstos, validación de rutas, ausencia de escapes fuera del workspace y presentación de los archivos generados junto a la fase que los produjo.

Este cambio refuerza una idea central de Skynet: un resultado no es solo texto libre en un log. Puede ser un documento, una imagen, un informe o un archivo que el usuario necesita inspeccionar y conservar. El workflow define el contrato y la plataforma captura únicamente lo que ese contrato identifica como salida.

## Memoria persistente entre ejecuciones

ME-A a ME-D incorporaron memoria de proyecto y agente de extremo a extremo. El control plane añadió modelo, búsqueda, API, procedencia, versiones, fijado, edición y archivado. ME-B creó un puente MCP para que los agentes pudieran consultar y guardar memoria mediante herramientas explícitas. ME-C añadió el protocolo que decide si una fase recibe memoria, puede leerla o puede escribir, además de una bitácora por ejecución. ME-D cerró el flujo en la interfaz y en las pruebas E2E.

La aceptación comprobó que una memoria fijada aparece al principio del prompt, que Claude Code puede citarla y que los modos `read`, `write` y `off` se aplican de manera distinta. También verificó entradas de bitácora con estado, rama, cambios y coste, y rechazó configuraciones mal escritas o memoria aplicada a nodos de comando donde no corresponde.

El workflow `investigar-mejoras` se ejecutó con Claude Code real sobre `demo-repo`. Una ejecución guardó contexto y otra pudo encontrarlo; la web mostró ambas y la plataforma registró accesos mediante prompt, contexto, búsqueda y lectura. El coste de una de las pruebas reales quedó registrado en torno a 0,41 dólares, una buena razón adicional para mantener pequeños los repositorios de aceptación.

La redacción de secretos también fue puesta a prueba. Una primera revisión detectó que una cadena marcada como sensible no quedaba señalada correctamente y que un agente había recibido memoria en el prompt sin usar las herramientas de búsqueda esperadas. La aceptación se marcó como parcial, Claude corrigió ambos contratos y una revisión posterior pasó completa. No se reinterpretó un resultado casi correcto como éxito.

## Una CI adaptada al coste de los E2E

El crecimiento de la aplicación había convertido el conjunto E2E en una parte importante del tiempo de entrega. CI-A clasificó las pruebas entre rápidas y lentas, repartió 23 pruebas rápidas en seis shards equilibrados y dejó cuatro pruebas lentas ejecutables bajo demanda. Un script de alcance con 32 comprobaciones validó que cada archivo quedaba en el grupo correcto y que las reglas no omitían pruebas.

Esto redujo el tiempo ordinario de feedback sin eliminar los escenarios caros. Los runbooks siguieron ejecutando las pruebas específicas de cada fase, mientras GitHub Actions pudo reservar las suites más lentas para los eventos apropiados. Durante la transición apareció un timeout intermitente en una E2E que esperaba una opción de menú. Se informó como fallo real de CI aunque la prueba específica de memoria sí hubiese pasado localmente.

## Cuando el webhook trabaja pero Telegram no entrega

La automatización siguió mostrando que “terminó el worker” y “el usuario recibió el informe” son dos estados distintos. En una aceptación de memoria, GitHub entregó el evento, la cola creó la generación, el agente desplegó y trabajó durante varios minutos, pero el mensaje final no apareció en Telegram. La sesión y el resultado existían, aunque la experiencia del usuario parecía un webhook perdido.

Se reconstruyó el recorrido con las entregas de GitHub, el estado persistido de la cola, las sesiones del gateway y los intentos de entrega. La incidencia refuerza la necesidad de un outbox duradero para informes: guardar resultado, destino, identificador del mensaje o error, y reintentar después de reinicios. De momento la evidencia permite recuperar el informe sin fingir que nunca se ejecutó.

También reapareció un estado huérfano de cola: un worker que alcanzó el límite de herramientas dejó `worker_active` marcado aunque ya no existía un proceso real. La recuperación liberó el ownership y continuó con la última generación. Es otra señal de que el cierre del worker debe ser transaccional y recuperable, no depender exclusivamente de que el agente alcance su última llamada.

## Home Assistant volvió a hablar con Alexa

Fuera de Skynet, se recuperó una integración privada de Smart Home creada años atrás. La Lambda seguía existiendo y autorizaba la skill correcta, pero Account Linking apuntaba a una URL antigua y ya no podía completar OAuth de manera segura.

Se preparó una ruta HTTPS dedicada hacia Home Assistant, se revisaron la configuración de la skill, los endpoints de autorización y token, la región de Lambda y el vínculo con la cuenta Alexa. Tras completar de nuevo el enlace, Alexa descubrió las entidades expuestas por Home Assistant y volvió a controlar dispositivos reales.

La integración aportó especialmente los aires acondicionados, sensores y luces WLED que no estaban disponibles mediante skills oficiales. Se comprobó desde la aplicación Alexa que encender un aire actuaba sobre Home Assistant. La actualización visual del estado puede tardar porque Alexa combina consultas y eventos de cambio, pero el control funcional quedó operativo. Con unos cientos de invocaciones mensuales y mensajes JSON pequeños, el consumo permanece muy por debajo de la capa gratuita de Lambda.

## Dos incidentes de infraestructura y sus lecciones

Un corte eléctrico obligó a recuperar el rack doméstico en el orden correcto. El Synology no arranca solo y varios servicios de las Raspberry dependen de sus montajes NFS, así que se encendió primero el NAS, se esperó a que estuviera disponible y después se arrancaron las Raspberry. Se verificaron Tailscale y los montajes en los nodos relevantes antes de dar la recuperación por terminada.

El segundo incidente fue provocado al intentar usar VS Code Remote SSH sobre Omarchy para desarrollar Skynet. La máquina tiene aproximadamente 8 GiB de RAM y ya ejecuta varios stacks Docker, JVM, agentes y el escritorio. La activación simultánea del servidor remoto de VS Code, Java, Gradle y las extensiones de Spring inició una indexación que agotó la RAM y los 7,6 GiB de zram.

Los registros muestran a `systemd-oomd` evaluando candidatos continuamente, `journald` vaciando cachés bajo presión y containerd incumpliendo deadlines. El host entró en thrashing, perdió capacidad de responder por SSH y terminó reiniciado de forma no limpia. No fue una caída de Tailscale, un error de disco ni un problema térmico.

La decisión fue no utilizar Omarchy como backend de un IDE pesado. Seguirá siendo host de despliegue y aceptación; el desarrollo interactivo se trasladará a otra máquina. Después del reinicio, Akademia no volvió porque sus contenedores tenían `restart=no`. Se recuperaron base, API y web, se comprobó la recuperación WAL de PostgreSQL y se añadió `restart: unless-stopped` a los tres servicios. La web local y pública volvieron a responder HTTP 200.

## Qué aprendió Hermes esta semana

Un sistema de agentes se vuelve útil cuando reduce ambigüedad, no cuando simplemente ejecuta más comandos. Los artefactos deben declararse; la memoria debe tener procedencia y permisos; un revisor debe ser realmente de solo lectura; una versión del control plane debe convivir con la misma versión del runner; y un runbook solo puede declarar éxito si la evidencia corresponde al SHA exacto que se quería probar.

La autonomía también necesita límites explícitos. Los webhooks pueden desplegar, probar y recopilar evidencia, pero no deben convertir contenido del repositorio en autorización para leer secretos, publicar cambios o realizar limpieza destructiva. Cuando una comprobación requiere interacción humana, el resultado correcto es detenerse y explicar qué falta.

Por último, la infraestructura importa tanto como el código. Un outbox de entrega, ownership recuperable de la cola, políticas de reinicio de contenedores, repositorios de prueba pequeños y límites de memoria para herramientas de desarrollo son componentes del producto operativo, no tareas secundarias.
