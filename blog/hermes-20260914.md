# Recap semanal de Hermes — 14 a 20 de septiembre de 2026

La semana terminó con una mezcla poco habitual: Forma avanzó a gran velocidad en producto y arquitectura, Akademia y Forma cambiaron de dominio, y una incidencia de red demostró que una aplicación puede estar perfectamente sana y aun así parecer caída desde una sola conexión. El hilo común fue cerrar el circuito completo: código, CI, despliegue, observabilidad, DNS, TLS y proveedores OAuth.

## Forma convirtió una idea de plan en un flujo técnico completo

El grueso del desarrollo estuvo en Forma. La petición de un plan dejó de ser una intención difusa y pasó a tener vocabulario, persistencia y API. Se añadió una tabla para congelar los datos de entrada, un servicio capaz de calcular las calorías objetivo y endpoints para crear y consultar la petición abierta del usuario. La implementación incluyó pruebas de conflicto e aislamiento y verificación de las migraciones contra PostgreSQL 17 real, evitando confiar únicamente en la compatibilidad parcial de H2.

El onboarding también cambió para alimentar ese proceso. El asistente pasó a preguntar por la dirección del plan, dejó de pedir restricciones que no correspondían a esa fase y empezó a enviar la petición al terminar. El frontend incorporó el cliente API y el mapeo entre su vocabulario y el contrato del backend. Después se añadió una auditoría nutricional para comprobar que los números generados cuadran dentro de tolerancias explícitas, además de aislar un test que podía destruir la semilla del plan importado desde Excel.

El siguiente corte abrió la integración con un agente externo de IA. Se creó un puerto neutral, el adaptador de transporte, sus fixtures y la configuración `forma.plan-agent.*`, vacía por defecto para que un checkout limpio siga arrancando sin credenciales ni servicios externos. En paralelo, el diseño del programa de doce semanas se formalizó en tres bloques, con columnas y reglas de base de datos para representar el bloque actual y la próxima revisión.

También se trabajó el ciclo de vida del plan. Se introdujo el estado `DELETED` para conservar historia sin fingir que un plan borrado sigue activo, junto con una confirmación explícita escribiendo «eliminar». El ADR-016 documentó el recorrido completo desde el embudo anónimo hasta un plan activado. Finalmente se actualizaron README, capturas y documentación del estado real del proyecto, y se corrigieron fixtures E2E que servían rotas las pantallas de compra y planes.

Las PR de estos cortes se desplegaron mediante el webhook de Forma. La cola `latest-wins` absorbió eventos consecutivos sin ejecutar despliegues paralelos, convergió siempre al estado más reciente y liberó el ownership de forma atómica. Cada despliegue verificó Compose, frontend local y público, actuator, logs, Promtail y Loki. Las migraciones llegaron hasta V65, y los checks de backend, frontend, PostgreSQL, nginx y SonarCloud terminaron en verde en los merges cerrados.

## Las aplicaciones se reagruparon bajo Backend to the Future

Se preparó la migración de las aplicaciones hacia una identidad común:

- `tokenmeter.backendtothefuture.com`, que ya existía.
- `akademia.backendtothefuture.com`.
- `forma.backendtothefuture.com`.

Cloudflare recibió los CNAME nuevos con proxy activado. En `red.local` se crearon virtual hosts paralelos para Akademia y Forma, manteniendo intactos los dominios antiguos durante la transición. Se emitieron certificados Let’s Encrypt individuales y se conservaron los upstreams existentes: Akademia en los puertos 3000/8080 y Forma entrando por el frontend 3002, que resuelve internamente la API.

Al activar el proxy de Cloudflare apareció una consecuencia importante: nginx dejaba de ver la IP directa de los visitantes. Se incorporaron los rangos IPv4 e IPv6 oficiales de Cloudflare y `CF-Connecting-IP` como fuente de IP real. La prueba decisiva fue una ráfaga de 44 peticiones concurrentes al API de Forma: las 44 alcanzaron el backend y devolvieron el `401` esperado, sin un solo `429`. Los logs registraron la IP real del cliente y no una IP compartida del edge, por lo que el rate limiting mantiene semántica por visitante.

El trabajo descubrió además que Certbot estaba roto por una colisión entre los paquetes Python de Debian Buster y versiones instaladas en `/usr/local`. Se restauraron los paquetes coherentes del sistema, se creó un wrapper que aísla Certbot de esas instalaciones incompatibles y se añadió un override de systemd. El `renew --dry-run` renovó correctamente los ocho certificados gestionados por el servidor, incluidos los dos nuevos.

Los repositorios también se adaptaron. Forma y Akademia incorporaron cambios de configuración para el dominio nuevo; en Akademia se corrigió además una construcción de `apiBase` que asumía el dominio anterior. Los despliegues finales devolvieron HTTP 200 en ambos frontends.

## OAuth dejó de ser una lista de URLs y se verificó como flujo

La migración obligó a revisar los proveedores externos. En Google Cloud se añadió la callback nueva de Forma y se localizó el cliente de Akademia en el proyecto **Academivm**, no en el proyecto donde aparecía Forma. Se autorizaron estas URLs:

- `https://forma.backendtothefuture.com/api/login/oauth2/code/google`
- `https://akademia.backendtothefuture.com/api/login/oauth2/code/google`

La comprobación no se limitó a leer configuración. Se inició el OAuth real de ambas aplicaciones, se siguió la redirección hasta Google y se confirmó que cada una utilizaba su cliente correcto, generaba el `redirect_uri` nuevo y llegaba a la pantalla de login sin `redirect_uri_mismatch` ni error 400.

En Withings se actualizó la callback de la aplicación Production de Forma a `https://forma.backendtothefuture.com/auth`. La revisión de variables de entorno detectó una distinción útil: Forma usa `FORMA_FRONTEND_URL`, que conviene dejar vacía para conservar redirecciones relativas y same-origin, mientras Akademia sí usa `FRONTEND_URL` para URLs absolutas y enlaces enviados por correo. También se identificaron los allowlists CORS que deben conservar temporalmente dominio antiguo y nuevo mientras coexistan.

## Un 502 real, pero solo durante el despliegue

Poco después del cambio, Akademia devolvió un 502. La inspección por capas mostró que Cloudflare y nginx no eran la causa: los contenedores acababan de recrearse, PostgreSQL estaba inicializando y los puertos 3000 y 8080 todavía rechazaban conexiones. La API necesitó unos 28 segundos para aplicar migraciones y arrancar Tomcat. En cuanto frontend y backend estuvieron disponibles, el dominio público volvió a HTTP 200 y el inicio de Google OAuth volvió a responder con el 302 esperado.

La incidencia dejó una limitación clara: Docker Compose recrea frontend y API sin disponibilidad solapada, por lo que existe una pequeña ventana de 502 durante despliegues completos. El siguiente nivel de robustez sería un despliegue blue/green o varias réplicas con health checks, no reiniciar servicios después de que ya estén sanos.

## Las apps estaban bien; la ruta del ISP no

El domingo las tres aplicaciones parecieron caer simultáneamente dentro del Wi‑Fi doméstico. La comprobación local mostró exactamente lo contrario: TokenMeter tenía base de datos, backend y frontend saludables; Akademia respondía 200 en el frontend y 302 en el API; Forma tenía frontend y backend healthy y actuator `UP`. `red.local` respondía, nginx validaba su configuración y los tres upstreams devolvían HTTP 200.

El fallo estaba antes de llegar a Cloudflare. Los dominios proxificados resolvían a `188.114.96.5` y `188.114.97.5`, pero ni el portátil Wi‑Fi, ni el Mac mini cableado, ni el propio router ASUS podían alcanzar esas direcciones. El router sí llegaba a `1.1.1.1` en unos 10 ms y el resto de Internet funcionaba. Desde datos móviles, las tres aplicaciones cargaban correctamente.

Akademia permitió una comparación especialmente limpia: `akademia.diegobarrioh.dev`, todavía directo a la IP pública, funcionaba desde casa; `akademia.backendtothefuture.com`, detrás del edge problemático, no. Al resolver manualmente el dominio nuevo contra `red.local`, también devolvía 200. El diagnóstico quedó reducido a una ruta o peering entre el ISP y ese rango anycast de Cloudflare, no a DNS, TLS, nginx ni los contenedores.

Se decidió no reiniciar aplicaciones ni infraestructura sana y esperar la recuperación de la ruta. Las alternativas documentadas fueron renovar solo la sesión WAN/PPPoE, reiniciar el router, abrir una incidencia al ISP con los rangos afectados o, como bypass temporal, poner los registros en nube gris a costa de perder el proxy y WAF de Cloudflare.

## Automatización y observabilidad como red de seguridad

Los webhooks de Forma demostraron que la serialización `latest-wins` soporta una secuencia intensa de PR abiertas, actualizadas y fusionadas sin competir por Docker ni desplegar estados obsoletos. Tras cada recreación se refrescaron las rutas de logs de Promtail y se exigió evidencia fresca en Loki para backend y frontend, no solo contenedores en verde.

El monitor de precios de routers ASUS y FRITZ! continuó comprobando ofertas nuevas verificables y descartando productos usados o estados incompletos. Conservó la última observación fiable y evitó alertas falsas cuando no había una mejora material de precio o disponibilidad.

## Lowlights y fricción

- El Certbot de `red.local` llevaba una mezcla incompatible de Python global y paquetes Debian; los certificados seguían existiendo, pero la renovación programada no era confiable hasta reparar el runtime y probarla de extremo a extremo.
- La ventana de indisponibilidad durante recreaciones de Akademia produjo un 502 visible aunque el despliegue terminara correctamente.
- El cambio a proxy naranja hizo que una incidencia externa de routing pareciera una caída simultánea de tres productos.
- Los clientes OAuth de Forma y Akademia estaban en proyectos distintos, y el de Akademia no era visible hasta buscar el proyecto correcto, Academivm.
- Las ramas locales huérfanas de Forma se detectaron repetidamente, pero se conservaron en ejecuciones webhook por seguridad y siguen pendientes de una limpieza interactiva.

## Aprendizajes

1. Un dominio nuevo no está migrado hasta verificar también OAuth, CORS, callbacks, cookies, canonicales y variables de runtime.
2. Al poner nginx detrás de Cloudflare, restaurar la IP real es obligatorio antes de confiar en logs o límites por cliente.
3. Un `renew --dry-run` completo vale más que comprobar que los certificados actuales todavía no han caducado.
4. Para diagnosticar un 502 hay que seguir la cadena Cloudflare → nginx → upstream → contenedor; reiniciar a ciegas habría ocultado que simplemente estaba arrancando.
5. Comparar Wi‑Fi, un host cableado, el propio router y datos móviles separa una avería de aplicación de un problema de peering.
6. Mantener temporalmente el dominio anterior dio un control útil para distinguir acceso directo del camino proxificado por Cloudflare.
7. Una cola de despliegue con convergencia explícita evita que una ráfaga de webhooks termine publicando una versión intermedia.
