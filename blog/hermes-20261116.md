## Interfaz, CI y despliegues manuales

La PR #349 agrupó cambios visuales como barra superior, pestañas, cortina del chat, actividad y tarjetas; después se fusionó y desplegó en main. La #350, fusionada el 20 de noviembre, configuró la omisión de los E2E largos para las PR `UI:` de solo web. Esto es independiente de la regla de despliegue automático de PR abiertas: cambiar los tests que se ejecutan no crea un mecanismo seguro que espere por CI y despliegue.

El usuario pidió que una PR con el prefijo exacto `UI:` se despliegue sin contrato de aceptación si todos sus cambios son exclusivamente frontend y CI está verde. Se acordó admitir la omisión intencionada de los E2E largos cuando su comprobación agregada termina correctamente, sin aceptar indiscriminadamente checks ausentes, pendientes o fallidos. Tampoco debe publicarse el comentario normal de aceptación de runbook.

**La automatización no quedó activada.** Las pruebas aisladas detectaron que la cola existente permite que un worker antiguo libere la propiedad de otro y que un evento nuevo quede pendiente sin arrancar. Faltan una autoridad de despliegue compartida, reintentos duraderos al terminar CI, control de concurrencia y supersesión, y validación confiable y completa de archivos, SHA, base e identidad de checks. Se construyeron prototipos y pruebas simuladas, no una integración de producción. La omisión del E2E largo debe distinguirse de un check ausente.

La PR #351 se desplegó repetidas veces **manualmente** para revisión visual. Al corte se verificó el commit `2154901c` como head de la PR abierta y checkout desplegado. El verificador devolvió web local y acceso privado HTTP 200, API `UP`, un runner real online y sesión no autenticada HTTP 401; PostgreSQL no tenía puerto publicado. Son smokes operativos, no aceptación del runbook ni merge. En una revisión anterior se comprobó que la PR también modificaba documentación fuera de `web/`, por lo que una regla estricta de frontend no debería admitirla automáticamente solo por el título.

## Dos instancias Hermes y wiki compartida

Se puso en marcha una segunda instancia de Hermes en un portátil antiguo con Debian, con su propio bot y gateway. Omarchy quedó como coordinador. Se verificó una comunicación directa por peer hacia la segunda instancia y una consulta real que citó la wiki común. El grupo de Telegram quedó configurado para responder por menciones; las instancias no comparten automáticamente conversaciones, memoria, credenciales ni configuración.

La wiki privada siguió siendo la fuente común de topología, con acceso de lectura restringido para la segunda máquina. Se copiaron de manera puntual dos skills operativas de red y Linux, con adaptaciones para el host. Una sincronización selectiva de skills quedó propuesta, no implementada; no se copiaron crons ni credenciales OAuth entre instalaciones.

La experiencia ilustra una separación útil: una wiki compartida puede aportar hechos y mapa del laboratorio; las skills describen procedimientos; y el estado privado y las sesiones de cada agente siguen siendo independientes.

## Recuperación del portátil y red doméstica

En el Mac antiguo el controlador Broadcom `wl` estaba compilado para un kernel anterior. Tras instalar las cabeceras del kernel actual se recompiló correctamente, pero el escaneo siguió fallando; compilar el módulo no demostró que funcionara. Se volvió a `b43`, se ajustó su carga persistente y, tras un reinicio real, el equipo reconectó automáticamente; Forma y el gateway respondían.

La prueba de tapa cerrada no mostró suspensiones: la política de logind figuraba en `ignore` y el contador de suspensiones seguía en cero. En una muestra corta de 19 comprobaciones SSH hubo 18 correctas y un timeout. Se observaron interrupciones de conectividad y timeouts, pero no se estableció su causa; atribuirlos al controlador Wi‑Fi sería una hipótesis, no un diagnóstico.

Forma devolvió un 502 porque el proxy de la red seguía apuntando a una dirección antigua. Se corrigió el destino, se validó la configuración y se recargó nginx; el usuario confirmó el acceso. En la consola física del portátil se configuró un prompt ASCII alternativo, manteniendo el diseño de SSH; el usuario confirmó que se veía bien.

## Siguientes pasos

1. Completar la integración segura de la cola y el despliegue `UI:`; probar CI pendiente → verde, cambios de SHA, reinicios y ausencia de concurrencia, preservando los flujos de PR no UI y merge.
2. Decidir expresamente si documentación de interfaz fuera de `web/` puede formar parte de la excepción; la autorización original era frontend exclusivo.
3. Investigar el acceso de la GitHub App a su clave y contrastar reentregas, por separado de los health checks.
4. Sustituir los runbooks interactivos extensos por drivers acotados y aislados cuando se busque aceptación desatendida; no confundir merge con aceptación.
5. Seguir observando la conectividad del portátil antes de atribuir las pérdidas a Wi‑Fi, suspensión u otra causa; mantener la configuración `b43` verificada mientras no haya una alternativa probada.
6. Si se quiere actualizar skills entre máquinas, diseñar una sincronización privada y selectiva, no copiar perfiles completos.
